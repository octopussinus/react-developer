# React Developer CLI — Enterprise Readiness Audit

**Date:** 2026-10-01
**Audited commit:** `b78e5f8` (branch `main`)
**Scope:** `src/specify_cli/` (1474 LOC), `templates/commands/` (8 files, 87 KB), `react-template/`, `expo-template/`
**Method:** full static read of the CLI, every command template, both project templates; plus a survey of competing/complementary tooling (sources at the end).

**The three questions this report answers:**

1. Where are the bottlenecks that stop this from producing **enterprise-grade** frontend apps?
2. How do we make the output **easy to check** — by a reviewer and by the agent itself?
3. How does a user **feed useful information back to the AI** about what should be improved?

Every bottleneck below carries a concrete proposed fix. Section 3 designs the two capabilities you asked for. Section 4 compares alternatives and gives a build-vs-adopt recommendation.

---

## TL;DR — Verdict

The idea is right and the niche is real: **an opinionated, agent-agnostic React/Expo workflow installer**. Nobody else does exactly this. But in its current shape the project optimizes the *generation* half of the loop and has essentially nothing for the *verification* and *correction* halves — which is where enterprise work actually lives.

Three structural problems dominate everything else:

| # | Problem | One-line consequence |
|---|---------|----------------------|
| **1** | **No verification layer at all.** Zero test tooling in either template — no Vitest, Jest, Playwright, Testing Library, Storybook, CI, or `typecheck` script. | Neither a reviewer nor the agent can tell whether generated code works. The whole "easy to check" goal is unmet at the foundation. |
| **2** | **No durable project memory.** No `AGENTS.md` / `CLAUDE.md`, no constitution, no rules file. All 87 KB of knowledge is locked inside slash commands that only load when typed. | Normal conversational work — most real usage — runs with **zero** project rules. Every human correction is forgotten when the session ends. |
| **3** | **Template is a vendored dashboard, not an architecture.** `react-template` is a copy of TailAdmin: type-based folders, magic filename routing, 30 UI dependencies, ~90 demo images, no data/state/validation layer. | At 5 pages it looks fine. At 50 pages generated by an agent, everything piles into shared buckets with nothing preventing drift. |

Scorecard:

| Dimension | Score | Note |
|-----------|:-----:|------|
| Workflow concept & agent coverage (9 assistants) | 🟢 **4/5** | Genuine differentiator. Keep this. |
| Prompt engineering depth | 🟡 **3/5** | Detailed, but oversized, duplicated, no progressive disclosure. |

## Part 1 — What the project is today

```
react-dev init <name> --type react|react-native --ai <9 choices>
          │
          ├─ copy_react_template_files()   → react-template/ or expo-template/ verbatim
          ├─ generate_react_commands()     → copy templates/commands/react-*.md
          │                                   into .claude/commands/ | .github/prompts/ | ... (9 targets)
          └─ init_git_repo()
```

Then the human drives a 4-step linear chain in their assistant:

```
/react-prototype-creator  →  /react-requirements-creator  →  /react-typescript-developer  →  /react-page-developer
    prototypes/*.html            requirements/*.md               src/ logic                      src/pages/
```

Plus three side commands (`page-updater`, `language-creator`, `theme-creator`) and one orphan (`component-design`).

**The shape of the problem:** this is a one-directional pipeline. There is no gate between steps, no feedback edge going backwards, and no terminal verification. An agent can complete all four steps and produce code that does not compile, and nothing in the system would notice.

## Part 2 — Bottlenecks & Fixes

Severity: **P0** = broken or blocks enterprise adoption · **P1** = major · **P2** = moderate · **P3** = polish

### Category A — Verification: the output cannot be checked

---

#### A1 · 🔴 P0 — Zero test tooling in both templates

**Evidence.** A repo-wide grep for `vitest|jest|playwright|storybook|@testing-library` across all `package.json`/`ts`/`js` files returns **nothing**. `react-template/package.json` scripts are `dev`, `build`, `lint`, `preview`. `expo-template/package.json` scripts are `start`, `android`, `ios`, `web`, `lint`. No `test`. No `typecheck`. No `.github/workflows/`.

**Why it blocks you.** This is the root cause of the "easy to check" gap. Three distinct failures at once:
- **A reviewer** has nothing to run. Reviewing agent output becomes reading 600 lines of diff by eye.
- **The agent** has no feedback signal. It cannot self-correct because nothing tells it that it broke something. This is the single highest-leverage missing piece in the entire project — agents are dramatically more reliable when they can run a check and iterate.
- **CI** cannot gate anything, so quality depends entirely on human vigilance per PR.

**Fix.** Add a verification stack to both templates and expose it as one command the agent is instructed to run after every change.

```jsonc
// react-template/package.json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "typecheck": "tsc --noEmit",
    "lint": "eslint . --max-warnings=0",
    "format:check": "prettier --check .",
    "test": "vitest run --coverage",
    "test:watch": "vitest",
    "e2e": "playwright test",
    "a11y": "playwright test --grep @a11y",
    "deadcode": "knip",
    "storybook": "storybook dev -p 6006",
    "verify": "npm run format:check && npm run lint && npm run typecheck && npm run test && npm run deadcode"
  }
}
```

Dev dependencies: `vitest`, `@vitest/coverage-v8`, `@vitest/eslint-plugin`, `jsdom`, `@testing-library/react`, `@testing-library/user-event`, `@playwright/test`, `@axe-core/playwright`, `eslint-plugin-jsx-a11y`, `prettier`, `knip`, `storybook`.

For Expo: `jest-expo`, `@testing-library/react-native`, `eslint-config-expo`, plus [Maestro](https://maestro.mobile.dev) for E2E flows.

Then add a CI workflow to the template itself so every generated project is gated from commit #1:

```yaml
# .github/workflows/verify.yml
name: verify
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run verify
      - run: npx playwright install --with-deps chromium
      - run: npm run e2e
```

> **This is the #1 change.** Everything else in this report is worth less than this one item, because `npm run verify` is what turns an agent from "generates plausible code" into "generates code it has proven compiles, lints, passes tests, and has no dead exports."

#### A2 · 🔴 P0 — No agent self-verification step in the workflow

**Evidence.** The 4-step chain ends at `/react-page-developer`. `templates/commands/react-page-developer.md` ends with a self-review checklist of *prose assertions* ("✅ Use `useThemeColors()` for all colors") — the model grades its own homework from memory, with no execution.

**Why it blocks you.** Prose checklists are the weakest form of verification: the model that wrote the bug is asked to notice the bug, using the same flawed assumptions, without running anything.

**Fix.** Add a fifth command, `/react.verify`, that executes rather than asserts — and make steps 3 and 4 end by invoking it.

```markdown
---
description: Prove the last change works — build, lint, types, tests, a11y, and a real screenshot
---
# React Verify

Run these in order. Do NOT summarize as "done" until all pass.

1. `npm run verify` — fix every failure, then re-run. Never disable a rule to pass.
2. `npm run e2e` — if the feature has no E2E spec yet, write one first.
3. **Visual proof:** start the dev server, then use the Playwright MCP tools to
   navigate to the new route, take an accessibility snapshot, and take a screenshot
   at 375px, 768px and 1440px. Attach them to your report.
4. **Accessibility:** run axe against the new route. Report every violation with its
   impact level. Zero `critical` or `serious` violations is the merge bar.
5. Write the outcome to `specs/<feature>/review.md` under `## Automated verification`,
   including the exact commands run and their results.

## Report format
| Gate | Result | Detail |
|------|--------|--------|
| types / lint / unit / e2e / a11y / visual | pass \| FAIL | ... |

If any gate fails and you cannot fix it in 3 attempts, STOP and report the blocker.
Never report success for a gate you did not actually run.
```

Both [Playwright MCP](https://github.com/microsoft/playwright-mcp) and [Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp) give the agent real eyes here — accessibility-tree snapshots as structured text (cheap and reliable for assertions) plus pixel screenshots when layout/colour actually needs looking at. Ship an `.mcp.json` in the template so this works on day one:

```json
{
  "mcpServers": {
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] }
  }
}
```

#### A3 · 🟠 P1 — No visual review surface (Storybook) for a UI-generating tool

**Evidence.** No Storybook anywhere. The only way to look at a generated component is to run the whole app and navigate to the page that uses it.

**Why it blocks you.** For an *enterprise frontend* tool, "easy to check" means a reviewer can see every state of every component — empty, loading, error, long-text, RTL, dark mode — without clicking through the app. It is also the natural home for visual regression, which is the only automated way to catch "the agent silently changed the spacing on 40 cards."

**Fix.** Storybook + a story-per-component rule in `AGENTS.md`, and let the generator write stories as part of the component, not as an afterthought:

```tsx
// src/features/orders/components/OrderCard.stories.tsx
import type { Meta, StoryObj } from '@storybook/react-vite';
import { OrderCard } from './OrderCard';

const meta = { component: OrderCard, tags: ['autodocs'] } satisfies Meta<typeof OrderCard>;
export default meta;
type Story = StoryObj<typeof meta>;

export const Default: Story  = { args: { order: mockOrder } };
export const Loading: Story  = { args: { isLoading: true } };
export const Error: Story    = { args: { error: new Error('Network') } };
export const LongText: Story = { args: { order: { ...mockOrder, customer: 'ü'.repeat(80) } } };
```

Add visual regression on top — [Chromatic](https://www.chromatic.com/) (hosted, zero-config with Storybook) or self-hosted Playwright `toHaveScreenshot()`. The payoff specific to your use case: a PR comment showing *exactly which pixels the agent changed* is the single most reviewable artifact you can hand a human.

**Evidence.** `expo-template/package.json:10` declares `"lint": "eslint ."`, but `expo-template/` contains **no** `eslint.config.*` or `.eslintrc*`. ESLint 9 with no flat config exits with an error.

### Category B — Architecture: the template does not scale

---

#### B1 · 🔴 P0 — Type-based folders with no enforced boundaries

**Evidence.** `react-template/src/` is organized by technical kind:

```
src/components/{common,ecommerce,header,ui}/   src/pages/Dashboard/
src/context/   src/icons/   src/layout/   src/locales/   src/shared/{hooks,utils}/
```

116 files, no `features/` directory, nothing preventing any file from importing any other file. Worse, the root `README.md` documents a structure that **does not exist**: it promises `src/services/`, `src/types/`, `src/utils/` and `src/hooks/` — all four are absent (only `src/shared/hooks` and `src/shared/utils` exist).

**Why it blocks you.** This is the defining enterprise bottleneck. Type-based grouping works until roughly 10 screens; past that, `components/common/` becomes a 200-file junk drawer and every feature is smeared across six directories. It is *especially* corrosive with an agent, because the agent reads the existing structure to decide where new code goes — so the drift compounds on itself. And since the README describes imaginary folders, the agent will confidently create a *second*, parallel structure.

**Fix.** Adopt the feature-sliced layout from [bulletproof-react](https://github.com/alan2207/bulletproof-react) — the most widely referenced React architecture — and *enforce* it mechanically rather than hoping the prompt holds.

```
src/
├── app/                    # entry, providers, router
├── features/
│   └── orders/
│       ├── api/            # queries & mutations for this feature only
│       ├── components/     # components owned by this feature (+ .stories, + .test)
│       ├── hooks/
│       ├── types/
│       └── index.ts        # the ONLY public surface of the feature
├── components/ui/          # design system primitives (feature-agnostic)
├── lib/                    # api-client, i18n, utils
├── config/                 # env, routes, permissions
└── testing/                # test setup, render helpers, mock data
```

Two non-negotiable rules, both machine-checked:

1. **Unidirectional flow:** `app → features → components/ui → lib`. Never backwards.
2. **No cross-feature imports:** `features/a` may not import from `features/b`. Shared code graduates upward to `components/ui` or `lib`.

```js
// eslint.config.js — enforcement, not aspiration
import boundaries from 'eslint-plugin-boundaries';

export default [{
  plugins: { boundaries },
  settings: {
    'boundaries/elements': [
      { type: 'app',      pattern: 'src/app/*' },
      { type: 'feature',  pattern: 'src/features/*', capture: ['name'] },
      { type: 'ui',       pattern: 'src/components/*' },
      { type: 'lib',      pattern: 'src/lib/*' },
    ],
  },
  rules: {
    'boundaries/element-types': ['error', {
      default: 'disallow',
      rules: [
        { from: 'app',     allow: ['feature', 'ui', 'lib'] },
        // a feature may only import ITSELF, plus ui and lib
        { from: 'feature', allow: [['feature', { name: '${from.name}' }], 'ui', 'lib'] },
        { from: 'ui',      allow: ['ui', 'lib'] },
        { from: 'lib',     allow: ['lib'] },
      ],
    }],
  },
}];
```

Now "the agent put the file in the wrong place" is a **failing lint rule**, not a code-review conversation. Add `dependency-cruiser` on top if you also want a dependency graph image in CI.

#### B2 · 🟠 P1 — No data, state, or validation layer

**Evidence.** `react-template` dependencies include no server-state library (no TanStack Query / SWR), no client-state store (no Zustand / Redux), no schema validation (no Zod / Valibot), no form library (no React Hook Form). `react-template` contains **no API client at all** and no `.env.example` — the only env usage in the whole repo is `expo-template/services/api.ts:6`. Meanwhile `templates/commands/react-requirements-creator.md` has whole sections instructing the model to hand-invent "4. SERVICES", "5. VALIDATION FUNCTIONS" and "7. STATE MANAGEMENT" from scratch, every single time.

**Why it blocks you.** Asking an LLM to improvise a caching/retry/error strategy and a validation layer per feature guarantees N inconsistent implementations. And without a typed contract, the model **guesses API field names** — the most common and most expensive class of AI frontend bug, because it type-checks fine and fails in production.

**Fix.** Make these decisions once, in the template, so the agent assembles rather than invents:

| Concern | Choice | Why |
|---------|--------|-----|
| Server state | **TanStack Query** | Caching, retries, invalidation, devtools — all the logic the model would otherwise improvise. |
| Client state | **Zustand** | Minimal surface; hard to misuse. |
| Schemas | **Zod** | One schema → TS type + runtime validation + form resolver. |
| Forms | **React Hook Form** + `zodResolver` | Validation derives from the schema, never duplicated. |
| API types | **Generated from OpenAPI** | Kills the field-guessing bug class outright. |

The contract step matters most. Instead of letting the model write interfaces by hand, generate them:

```jsonc
"scripts": { "api:generate": "openapi-ts -i ./openapi.json -o ./src/lib/api/generated" }
```

[Hey API](https://heyapi.dev/) emits types, a client **and** Zod schemas from the spec. Then add to `AGENTS.md`: *"Never hand-write an API response type. Run `npm run api:generate` and import from `src/lib/api/generated`. If a field you need is missing, stop and say so — do not invent it."*

#### B3 · 🟠 P1 — `pageDiscovery` magic routing is a dead end

**Evidence.** `react-template/src/shared/utils/pageDiscovery.ts:11`:

```ts
const customPageModules = import.meta.glob('../pages/custom/*.tsx', { eager: true });
```

Route paths and sidebar labels are derived from the filename by regex; the component is read off `module.default` with an `as any` cast. The react-template README headlines this as "✨ Key Feature: automatic page discovery". **The globbed directory `src/pages/custom/` does not exist in the template** — so the advertised feature silently resolves to `{}` on a fresh project.

**Why it blocks you.** Six enterprise requirements are structurally impossible here: `eager: true` pulls every page into the main bundle (no code splitting — a 50-page app ships as one chunk); no route params (`/orders/:id`); no auth/role guards; no nested layouts; no per-route metadata (title, breadcrumb, i18n key, permission); no error boundaries or 404 semantics. Filename-derived labels also can't be translated — which is awkward in a template that ships i18n.

**Fix.** Replace magic with an explicit typed registry. It is barely more work for the agent to write and gives you everything above:

```ts
// src/config/routes.ts
export const routes = [
  {
    path: '/orders/:id',
    lazy: () => import('@/features/orders/pages/OrderDetail'),
    meta: {
      titleKey: 'orders.detail.title',
      permission: 'orders:read',
      breadcrumb: ['orders.list', 'orders.detail'],
      sidebar: { icon: 'package', group: 'commerce' },
    },
  },
] as const satisfies readonly RouteDef[];
```

The sidebar renders from `routes`, so registration stays a one-liner — but now it is typed, lazy, translatable, guardable, and reviewable in a diff. If you'd rather not own this, [TanStack Router](https://tanstack.com/router) gives type-safe params and loaders out of the box, and React Router 7 has file-route codegen.

#### B4 · 🟡 P2 — Dependency baggage and demo assets in every new project

**Evidence.** Every generated web project installs, whether used or not: 6 × `@fullcalendar/*`, `apexcharts` + `react-apexcharts`, 2 × `@react-jvectormap/*`, `swiper`, `flatpickr`, `react-dnd` + `react-dnd-html5-backend`, `react-dropzone`, `react-helmet-async`. Three of these need `overrides` in `package.json` to force React 19 compatibility — a signal they are unmaintained against current React. `i18next-http-backend` is installed and **never imported** (`src/i18n.ts` uses an eager glob instead). And `public/images/**` ships ~90 demo binaries into every repo — 37 stock user avatars, product photos, carousels, brand logos.

**Why it blocks you.** Supply-chain surface and audit noise you did not choose; `npm audit` findings you must triage for a calendar you never render; React-19 `overrides` that will eventually break; and a first commit full of stock photos of strangers. In a regulated enterprise, each unused transitive dependency is a real review cost.

**Fix.**
1. **Strip the core** to React + Router + Query + Zod + RHF + Tailwind + the design-system primitives.
2. **Make widgets opt-in** via a registry: `react-dev add chart`, `react-dev add calendar`. The [shadcn registry](https://ui.shadcn.com/docs/registry) format is the obvious vehicle — and it is agent-installable, so the model can pull a component on demand instead of you pre-installing twelve.
3. **Delete demo assets.** Ship 2–3 placeholder SVGs.
4. Drop `react-helmet-async` (React 19 hoists `<title>`/`<meta>` natively) and `i18next-http-backend` (unused).

#### B5 · 🟡 P2 — i18n: eager-loads all languages, keys untyped

**Evidence.** `react-template/src/i18n.ts:7` eagerly globs `./locales/*/*.json` into one `resources` object, assigned through `Record<string, any>` with an `@ts-ignore`. `/react-language-creator` is designed to add more languages to that glob.

**Why it blocks you.** Two scaling problems. (a) Every language ships to every user in the main bundle — add the 10 locales an enterprise rollout needs and all users download all 10. (b) `t('some.key')` is an untyped string: a missing or renamed key fails silently at runtime, which no test and no lint rule will catch. Both get worse exactly as the tool succeeds at adding languages.

**Fix.** Lazy-load namespaces per locale and type the keys:

```ts
// lazy: only the active locale's namespace is fetched
i18n.use(resourcesToBackend(
  (lng: string, ns: string) => import(`./locales/${lng}/${ns}.json`)
));
```

```ts
// src/types/i18next.d.ts — makes t() autocomplete and fail at compile time
import en from '../locales/en/common.json';
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common';
    resources: { common: typeof en };
  }
}
```

Add `eslint-plugin-i18next` to ban literal strings in JSX, and a CI check that every locale has the same key set as `en`. Then `/react-language-creator` can't produce a half-translated locale without CI noticing.

#### B6 · 🟠 P1 — The Expo template contradicts itself on styling

**Evidence.** `expo-template` ships NativeWind v4, `global.css`, `tailwind.config.js`, `nativewind-env.d.ts` and `tailwindcss@^3.4.0`. A grep for `className=` across `expo-template/components/` and `expo-template/app/` returns **zero matches** — every component uses `StyleSheet` + `useThemeColors()` instead. So the entire NativeWind toolchain is configured, installed, and unused. `README.md:132` compounds it by documenting the StyleSheet approach while the dependencies claim the other one.

**Why it blocks you.** It breaks the core premise of the product for mobile. The pipeline's value is *prototype in Tailwind → carry those classes into code*; `react-page-developer.md:31` even says "replace `class=` with `className=`, **preserve all Tailwind classes**". On the Expo path that is impossible — someone must hand-translate every utility class into `StyleSheet` objects, which is lossy, slow, and exactly the error-prone grunt work you wanted automated. Meanwhile the unused Babel/Metro/Tailwind config is live breakage surface on every Expo SDK bump.

**Fix — pick one, and make the whole stack agree:**

- **Option A (recommended): commit to NativeWind.** Convert the template's components to `className`, keep the config, and the prototype → code step becomes nearly mechanical on both platforms. One styling mental model for web and mobile.
- **Option B: remove NativeWind.** Delete `global.css`, `tailwind.config.js`, `nativewind-env.d.ts`, and both Tailwind deps; make `/react-prototype-creator` emit a **token-based** spec for mobile (spacing scale, colour roles, type ramp) instead of utility classes, so the translation step is at least well-defined.

Either way, record the decision in `AGENTS.md` so the agent stops seeing both signals at once.

### Category C — Workflow: linear, ungated, no traceability

---

#### C1 · 🟠 P1 — No clarification gate, no consistency gate

**Evidence.** The chain is `prototype → requirements → typescript → page`. Nothing between the steps validates anything. `react-requirements-creator.md` instructs the model to produce a 10-section spec from whatever it was given, with no mechanism to ask about ambiguity first and no check that step 4's code matches step 2's spec.

**Why it blocks you.** The expensive failure in spec-driven work is a confident spec built on a wrong assumption — it then propagates silently through code and tests. Mature SDD toolchains all converged on the same answer: explicit gates. GitHub's [Spec Kit](https://github.github.com/spec-kit/) ships `/speckit.clarify` (the agent asks up to 5 targeted questions and writes the answers *into* the spec) and `/speckit.analyze` (cross-checks spec ↔ plan ↔ tasks ↔ constitution for drift). Those two commands are the difference between a demo and a process.

**Fix.** Add three gates:

| New command | Role |
|---|---|
| `/react.constitution` | **Once per project.** Writes `AGENTS.md` — stack, architecture rules, test bar, a11y bar, i18n rules, definition of done. Every later command must cite it. |
| `/react.clarify` | After requirements. Agent asks ≤5 highest-leverage questions **one at a time**, writes answers into the spec under `## Clarifications`, and must not proceed while a `[NEEDS CLARIFICATION]` marker remains. |
| `/react.analyze` | Before implementation. Cross-checks spec ↔ plan ↔ code ↔ constitution; reports contradictions, unimplemented requirements, and rules violated. Read-only — it reports, never fixes. |

Make `[NEEDS CLARIFICATION: ...]` a required marker in the requirements template and have `/react.analyze` fail on any that survive. That single convention prevents most silent-assumption failures.

#### C2 · 🟠 P1 — Global `prototypes/` + `requirements/` can't support two features at once

**Evidence.** `react-prototype-creator.md` is emphatic: *"**DELETE** any existing prototype files in the `prototypes/` folder"*, repeated four times including the closing line. Requirements go to flat `requirements/page-dashboard.md`. Both directories are global and single-tenant.

**Why it blocks you.** Two developers (or two agent sessions) on two features overwrite each other. There is no link from requirement → prototype → code → PR, so nobody can answer "what was this built from, and was it approved?" — a basic enterprise audit question. The mandated deletion also destroys the design history for *the feature you are still working on*.

**Fix.** One feature, one branch, one folder — colocate everything and stop deleting:

```
specs/
├── 001-order-tracking/
│   ├── prototype.html      # or prototype/ for multiple screens
│   ├── spec.md             # requirements + ## Clarifications
│   ├── plan.md             # technical approach
│   ├── tasks.md            # checklist the agent ticks as it goes
│   └── review.md           # human feedback + automated verification results
└── 002-invoice-export/
```

Have `react-dev` (or a `/react.feature` command) create the folder and the branch together, and drop the deletion instruction entirely — git is the history mechanism. This also makes PR review natural: the spec and the code arrive in the same diff.

#### C3 · 🟡 P2 — Prototype step uses a different Tailwind than the project

**Evidence.** `react-prototype-creator.md` mandates `<script src="https://cdn.tailwindcss.com"></script>` — the **Tailwind v3** play CDN, explicitly not for production. The project it feeds is **Tailwind v4**: `react-template/postcss.config.js` uses `@tailwindcss/postcss` and `src/index.css` uses `@import "tailwindcss"`.

**Why it blocks you.** The prototype is the contract for the implementation, and it is built against a different engine. v4 changed the default colour palette to OKLCH, moved configuration from `tailwind.config.js` into CSS `@theme`, and renamed/removed utilities. So classes that render correctly in the prototype can render differently — or not exist — in the app, and the mismatch surfaces as "the agent's code doesn't look like the design." Worse, the prototype knows nothing of the project's actual theme tokens, so the model invents `bg-gray-50` where your design system says `bg-surface-muted`.

**Fix.** Build prototypes **with the project's own Tailwind build and tokens**:

```html
<!-- specs/001-order-tracking/prototype.html -->
<link rel="stylesheet" href="/src/index.css" />  <!-- served by the project's Vite -->
```

Serve it with `npm run dev` (Vite serves arbitrary HTML entries), so the prototype gets v4, your `@theme` tokens, your fonts, and dark mode for free. Then update the command to *require* using existing design tokens and existing `components/ui` primitives, and to list any new token it needs instead of inventing a hex value. Pixel fidelity stops being a translation problem.

#### D1 · 🔴 P0 — No `AGENTS.md` / `CLAUDE.md` — the agent has no project memory

**Evidence.** A repo-wide search for `CLAUDE.md`, `AGENTS.md`, `.cursorrules` or any constitution file returns **nothing** in either template. All project knowledge lives in `templates/commands/*.md`, which load **only when a slash command is typed**.

**Why it blocks you.** This is the quiet killer. Most real work is conversational — "add a column to the orders table", "this button should be disabled while saving". None of that goes through a slash command, so **none of it sees any project rules**. The agent will reach for `fetch` instead of your query client, write a `StyleSheet` where the project uses NativeWind, put a component in `components/common/`, and skip the test — all consistent with the code it can see, all against your conventions. And because nothing is written down, the same correction is needed again tomorrow.

`AGENTS.md` has become the cross-tool standard for exactly this, and Nx's agent setup writes a `CLAUDE.md`/`AGENTS.md` as a first-class output for the same reason.

**Fix.** Generate `AGENTS.md` at `init` (symlink `CLAUDE.md` → it), keep it short and absolute:

```markdown
# AGENTS.md — project constitution
Non-negotiable. If a request conflicts with this file, say so before proceeding.

## Stack
React 19 · TypeScript (strict) · Vite · Tailwind v4 · TanStack Query · Zod · RHF · i18next

## Architecture — enforced by eslint-plugin-boundaries
- Feature code goes in `src/features/<feature>/`. Never in `src/components/common/`.
- A feature NEVER imports from another feature. Shared code graduates to `components/ui` or `lib`.
- Import direction: app → features → components/ui → lib. Never backwards.

## Hard rules
- NEVER hand-write an API response type. Run `npm run api:generate`.
  If a field is missing from the spec, STOP and report it. Do not invent fields.
- NEVER use `any`, `as any`, or `@ts-ignore`. No `eslint-disable` without an issue link.
- NEVER hardcode a user-facing string. Use `t('ns.key')` and add the key to every locale.
- NEVER hardcode a colour. Use design tokens from `src/styles/theme.css`.
- Every component gets a `.stories.tsx`. Every hook and every service gets a `.test.ts`.

## Definition of done
`npm run verify` passes · E2E spec exists for the happy path · zero serious axe violations
· screenshots at 375/768/1440 attached · `specs/<feature>/tasks.md` fully ticked

## Learned rules
<!-- /react.feedback appends here. These are real corrections from real reviews. -->
```

That last section is the hinge for D2.

#### D2 · 🔴 P0 — No structured channel for human → AI feedback

**Evidence.** The only feedback path today is typing prose into a chat window. There is no mechanism to point at a rendered element, no review artifact, and no place where a correction survives the session. `react-page-updater.md` handles *change requests* but reads nothing accumulated and writes nothing durable.

**Why it blocks you.** This is the capability you explicitly asked for, and it is the difference between a code generator and a system that improves. Today: you spot a problem on screen → you describe it in words → the agent guesses which of 116 files you mean → it fixes it → the knowledge evaporates. Tomorrow a different session reintroduces the same problem.

**Fix — three layers, each independently useful. Build them in this order.**

**Layer 1 — Visual, in-browser pointing (highest value per hour of work).**

Ship a dev-only toolbar in the template so the human can *click the thing* instead of describing it. The agent receives the DOM path, the React component name and source file, computed styles, and a screenshot:

| Tool | Shape | Notes |
|---|---|---|
| [**stagewise**](https://stagewise.io) | npm toolbar + framework packages (React/Next/Vue/Angular/Svelte); connects the browser to your editor's agent | Closest fit to what you described. Click element → comment → agent edits the local codebase. Open-source core; check the current licence/pricing split for commercial use. |
| [**Agentation**](https://github.com/benjitaylor/agentation) | Browser extension, agent-agnostic, MCP integration | Annotation modes (click, text-select, multi-select, draw region), auto selector generation, React component detection, computed styles. Emits structured output for *any* agent — good if you must stay 9-assistant neutral. |
| [**Onlook**](https://onlook.com) | Visual editor for React/Next | Constrains AI edits to your existing component library — strong design-system discipline. Heavier: closer to an editor than a feedback channel. |

The minimal version you could own yourself is ~150 lines: a dev-only overlay that captures `event.target`, walks up to the nearest component via React DevTools' fiber hook, grabs the source path from the JSX dev transform, and writes `{file, line, component, selector, computedStyles, screenshot, comment}` to `.ai/inbox/<ts>.json`. The agent reads the inbox. That removes the licensing question entirely and keeps you agent-neutral.

**Layer 2 — A durable review artifact.**

Give every feature a `review.md` the human edits directly — reviewable in a PR, diffable, and read by the agent on the next pass:

```markdown
# Review — 001-order-tracking

## Automated verification
| Gate | Result |
|---|---|
| types / lint / unit / e2e / a11y | pass |

## Human review
- [ ] **blocker** · `OrderCard.tsx:42` — status badge uses a raw hex. Use `--color-status-warning`.
- [ ] **should** · Empty state is missing. Every list needs empty + loading + error.
- [x] **nit** · Date format should be locale-aware (`Intl.DateTimeFormat`).

## Promote to rules?
- [x] "Every list component needs empty/loading/error states" → AGENTS.md
- [x] "No raw hex colours" → custom ESLint rule
```

**Layer 3 — Promotion: turn repeated corrections into permanent constraints.** *This is what makes the loop compound.*

```markdown
---
description: Capture feedback about generated code and promote recurring issues into permanent rules
---
# React Feedback

1. Read `.ai/inbox/*.json` (visual feedback) and every unchecked item in `specs/*/review.md`.
2. Append each item to `.ai/feedback.md` with: date, feature, file:line, category, the correction.
3. Count occurrences by category. For any category seen **3+ times**, propose a promotion:
   - **Mechanically checkable** → write a custom ESLint rule in `eslint-rules/` + a test for it,
     and wire it into `eslint.config.js`. Ask before adding (it will fail CI for everyone).
   - **Not mechanically checkable** → add one line to the `## Learned rules` section of AGENTS.md.
   - **A missing capability** → open an issue instead; don't paper over it with a rule.
4. Report: what you captured, what you promoted, what you're still watching (1–2 occurrences).

Never promote silently. Every new rule needs a one-line rationale citing the incidents that caused it.
```

The escalation ladder — *chat → feedback log → AGENTS.md rule → lint rule → CI gate* — is the whole point. A correction made once becomes a rule that can never be violated again. ([Evil Martians](https://evilmartians.com/chronicles/ten-anti-ai-slop-moves-for-frontend-projects-going-faster-than-humans-can-review) calls these "scars": lint rules that encode bugs you actually shipped.)

#### D3 · 🟡 P2 — No upgrade path; a project can't say which template it came from

**Evidence.** `init` copies files and exits. There is no `upgrade`/`sync` command, no version stamp written into the project, and no record of the choices made. Improve a prompt in `templates/commands/` and **every existing project keeps the old copy forever**.

**Why it blocks you.** Your 20th project will be running your 1st-generation prompts. Nobody can tell which generation a given repo is on, so fleet-wide fixes are impossible — which, for a tool whose value *is* its prompts, caps the whole product.

#### E2 · 🟠 P1 — TOML generation is unescaped and silently corruptible

**Evidence.** `src/specify_cli/__init__.py:1019-1021` builds Gemini/Qwen command files by f-string:

```python
toml_content = f'''description = "{description}"
prompt = """
{prompt_content}
"""
'''
```

`description` is taken verbatim from the markdown frontmatter, and `prompt_content` is the entire command body.

**Why it blocks you.** Any `"` in a description produces invalid TOML. Any `"""` or trailing backslash in a body — entirely plausible in prompts full of fenced code blocks — terminates the multi-line string early and corrupts the file. It fails **silently**: files are written, `init` reports success, and the user discovers it when `/react-page-developer` misbehaves in Gemini CLI. Today's 8 templates happen to be safe; the next edit might not be, and nothing would catch it.

**Fix.** Serialize properly and test the round trip:

```python
import tomli_w, tomllib

dest_file.write_bytes(tomli_w.dumps({
    "description": description,
    "prompt": prompt_content,
}).encode("utf-8"))

# test: every template, every agent, must parse back
assert tomllib.loads(dest_file.read_text())["prompt"] == prompt_content
```

## Part 3 — The two capabilities you asked for, designed

### 3.1 "Easy to check"

Checkability is not one feature; it is four surfaces, cheapest first. Each one catches what the one before it can't:

```
1. MACHINE, PRE-COMMIT     npm run verify
                           prettier · eslint (boundaries, jsx-a11y, sonarjs) · tsc · vitest · knip
                           → catches: wrong location, any, dead code, broken types, logic regressions

2. MACHINE, PRE-MERGE      CI: verify + playwright e2e + axe + visual regression + jscpd
                           → catches: broken flows, a11y violations, unintended pixel changes, copy-paste

3. HUMAN, VISUAL           Storybook (every state) + screenshots at 3 widths in the PR
                           → catches: "works but wrong" — bad empty states, overflow, contrast

4. HUMAN, SEMANTIC         specs/<feature>/review.md next to spec.md in the same diff
                           → catches: built the wrong thing / spec drift
```

Three force multipliers worth adopting from the [anti-AI-slop playbook](https://evilmartians.com/chronicles/ten-anti-ai-slop-moves-for-frontend-projects-going-faster-than-humans-can-review):

- **Mutation testing** ([Stryker](https://stryker-mutator.io/)) on the diff. LLMs write tests that assert almost nothing (`expect(result).toBeDefined()`). Stryker flips `<` to `<=` and empties arrays; surviving mutants are tests that don't test. This is how you check *the checks*.
- **`jscpd`** for duplicate detection. Agents copy-paste by nature; set a looser threshold for markup than for logic.
- **Strict TS beyond `strict`**: `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` force the undefined-handling that LLMs skip by default. Plus `eslint-plugin-sonarjs` (cognitive complexity), `react-you-might-not-need-an-effect` (the single most common React mistake in generated code), and `@vitest/eslint-plugin`'s `expect-expect`/`no-focused-tests`.

Then close the loop: `AGENTS.md` makes `npm run verify` part of the definition of done, and `/react.verify` makes the agent run it and report real results — so layers 1 and 2 execute *before* a human ever looks.

### 3.2 "User provides useful info to AI"

The system to build is an **escalation ladder**, where each rung is more durable than the last:

```
┌─ 1. POINT ────────────────────────────────────────────────────────────┐
│  Dev-only browser toolbar. Click the element, type the comment.       │
│  Agent gets: file:line · component · selector · computed styles ·     │
│  screenshot · your words                                              │
│  → stagewise / Agentation, or ~150 lines you own                      │
└───────────────────────────────┬───────────────────────────────────────┘
                                ▼  .ai/inbox/<ts>.json
┌─ 2. RECORD ───────────────────────────────────────────────────────────┐
│  specs/<feature>/review.md — blocker / should / nit, in the PR diff   │
└───────────────────────────────┬───────────────────────────────────────┘
                                ▼  /react.feedback
┌─ 3. ACCUMULATE ───────────────────────────────────────────────────────┐
│  .ai/feedback.md — every correction, categorized, counted             │
└───────────────────────────────┬───────────────────────────────────────┘
                                ▼  seen 3+ times?
┌─ 4. PROMOTE ──────────────────────────────────────────────────────────┐
│  mechanically checkable → custom ESLint rule → CI gate (can't recur)  │
│  judgment call          → AGENTS.md ## Learned rules (always in ctx)  │
│  missing capability     → GitHub issue (don't paper over it)          │
└───────────────────────────────────────────────────────────────────────┘
```

Why this specific shape: feedback typed into chat has a half-life of one session. Feedback that lands in a lint rule has a half-life of the project. The ladder's job is to move each correction as far down as it can honestly go — and the `3+ occurrences` threshold is what keeps you from ossifying a one-off preference into a rule everyone fights.
